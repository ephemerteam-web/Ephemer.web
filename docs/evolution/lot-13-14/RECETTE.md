## Protocole de référence sur copie — écarté pour cette livraison

Si une copie devient disponible ultérieurement, installer les quatre fichiers puis contrôler `verification-raccordement.sql`. Les indicateurs ne sont modifiables que par l'administrateur SQL. Régénérer les contrôles avec `node tools/prepare-collective-verification.mjs` après une modification SQL. N'ouvrir les indicateurs pour ces essais que dans un environnement sans fournisseur réel. L'activation actuelle contient le GO humain sans recette distante de cette livraison ; elle ne certifie pas ce protocole et n'est pas une activation de fixtures automatique.

`recette-copie.sql` attend un marqueur de copie et les UUID de trois comptes **synthétiques existants et vérifiés** dans des paramètres de session. Les noms sont dans l'en-tête du fichier. Renseigner ces paramètres humainement ; ne pas enlever les gardes et ne pas exécuter les fixtures dans la base de l'application. Aucun mot de passe/Bearer à copier dans un script ou une conversation. La recette usurpe volontairement les rôles depuis SQL sur la copie : elle doit être complétée par de vrais JWT via REST.

| Cas | Résultat exigé |

## Courses à deux sessions

Utiliser deux sessions SQL indépendantes de la copie. Dans chacune, renseigner le marqueur et les mêmes comptes synthétiques. Conserver les créations jetables ; le chevauchement des transactions doit être observé, pas supposé depuis des clics successifs.

1. **Édition contre fermeture** : partir d'une copie réinitialisée, exécuter `fixtures-concurrence.sql` (contrairement à la recette ordinaire, ce fichier COMMIT ses seules fixtures). Démarrer `concurrence-session-A.sql`, puis B pendant sa fenêtre de cinq secondes. Un seul gagnant ; l'autre reçoit un conflit récupérable. Exécuter `concurrence-verification.sql`. Une seconde exécution après la fin de A ne prouve pas un chevauchement.
2. **Réservation/engagement et annulation** : repartir des fixtures fraîches, ajouter `fixtures-email.sql`. Exécuter `concurrence-email-A.sql`, puis B pendant la fenêtre. B ne réserve pas une seconde fois et ne peut annoncer l'annulation après engagement. Les jetons restent dans des variables SQL ; aucun appel Resend.
3. **Annulation gagnante** : repartir des mêmes fixtures, exécuter la commande `annuler_programmation` avant A avec la révision courante. La réservation/prise en charge doit être refusée, sans `email_attempts` nouveau.
4. **Publication et retrait/départ** : partir d'une carte fermée/validée. La publication privilégiée et le retrait utilisent le verrou commun ; si publication gagne, le retrait révoque sa version ; si retrait gagne, la publication échoue faute de validation actuelle. Aucune lecture publique contenant le texte retiré après commit.
5. **Panne après réservation / après engagement / après acceptation simulée** : conserver les UUID, laisser expirer le bail de fixture sur copie ; une réservation jamais engagée est reprenable. Un engagement sans résultat reste incertain, sans nouvel essai. Appeler le rapprochement webhook avec un événement synthétique signé dans le serveur local simulé ; un doublon ou un événement `sent` retardé ne doit pas détruire `delivered`.
6. **Report, réouverture, révocation et suppression** contre engagement : la transaction arrivée avant engagement peut annuler ; celle arrivée après ne promet pas un rappel. Révocation bloque le lien même si l'email a été accepté.

Les fichiers de fixture contiennent des enveloppes **inutilisables** pour le transport réel. Ils ne doivent jamais servir à activer le worker réel ni à fabriquer un vrai lien de destinataire.

## Programmation et incidents

Tester séparément publication et email : pas avant leur instant UTC, heure inexistante refusée, heure double explicitement choisie, recalcul serveur identique. À 48 h exactement, reprise permise ; après, « À reprogrammer ». Une publication manquée bloque l'email. Le prochain passage est quotidien à 07 h UTC, sans promesse de seconde précise.

Tester la file par lots : les emails acceptés/échoués/incertains ne doivent pas occuper indéfiniment les 25 premières échéances. Un refus de quota reste à reprendre, pas « annulé ». Une perte d'organisation, une révocation ou un changement de destinataire bloque les travaux encore en attente. Les plafonds sont vérifiés dans la transaction d'engagement et ne se réinitialisent pas par suppression de contribution ou réessai.
